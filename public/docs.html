Introducción

La plataforma Macotrans expone tres APIs REST:

APIBase URLAutenticaciónPara quién

Todas las respuestas usan JSON con la forma { "data": ... } y los errores { "error": "mensaje" }.

Autenticación

Cada empresa cliente registrada en Macotrans recibe una API key (formato mk_…), gestionable desde el portal TMS (sección Empresas). Se envía en el encabezado X-API-Key de cada petición al API de integración. La clave delimita el alcance: cada empresa solo ve y opera sus propios pedidos.

curl -H "X-API-Key: mk_xxxxxxxxxxxxxxxx" \
     http://localhost:3000/api/integration/v1/me

El API pública del portal no requiere credenciales y el API interna es de uso del TMS (en producción quedaría detrás del login de operaciones).

API de integración (ERP / e-commerce)

El middleware de integración permite que sistemas externos creen pedidos que entran directo a la planificación consolidada de rutas de Macotrans, consulten su estado y reciban webhooks en su propio sistema. Soporta referencia externa (externalRef) para conciliar con el número de documento de tu ERP o el número de orden de tu e-commerce.

Módulo de carga del camión

Flujo completo desde el plan del ERP hasta la entrega confirmada:

PasoQué ocurre
1. ImportarPOST /api/v1/import recibe el plan en el mismo formato que se envía a Driv.in ({ clients: [...] }). Cada order del plan se registra como un bulto con su código de barras (alt_code); units_2 se interpreta como kg y units_3 como cm³.
2. OptimizarPOST /api/v1/optimize genera rutas propuestas usando solo vehículos aptos (campo apto del vehículo) y respetando capacidad en kg y m³.
3. AprobarPOST /api/v1/routes/{id}/approve: el usuario aprueba la propuesta y se genera la lista de carga en orden físico: volumétrica pesada a la delantera central, tubos a la parrilla, paquetería en orden inverso de entrega (LIFO).
4. CargarPOST /api/v1/routes/{id}/load con { "barcode": "..." } (escáner Bluetooth) o { "seq": n } (botón). Rechaza códigos ajenos a la ruta y bultos repetidos (HTTP 409).
5. DocumentosAl confirmar el último bulto se generan la guía de remisión y la factura por parada (clave de acceso de 49 dígitos, módulo 11), se envía el payload al webservice configurado en PUT /api/v1/billing-config y quedan el formato imprimible en /print/route/{id} y el JSON en GET /routes/{id}/documents.
6. DespacharPOST /routes/{id}/start solo procede con la carga completa. El GPS avanza y al llegar a cada cliente la parada queda en_sitio esperando al conductor.
7. EntregarPOST /routes/{id}/deliver con { orderId, resultado, bultoBarcodes, motivo, receptor }. resultado: entregado · entrega_parcial · devolucion · rechazado. El conductor usa la app móvil /conductor con el mismo escáner de la carga.
POST /api/v1/routes/RUT-1021/load
{ "barcode": "ST-26007438-B87-1000" }

→ 200
{ "data": { "bulto": { "seq": 1, "zone": "delantera-central", "loaded": true },
            "summary": { "loaded": 1, "total": 56, "complete": false },
            "loadStatus": "en_carga", "documentsGenerated": false } }

Optimización de rutas

El motor VRP asigna pedidos pendientes a los vehículos indicados usando barrido angular, vecino más cercano y mejora 2-opt, validando capacidad en kg y m³. Soporta dos modos:

  • Clásico: cada vehículo sale del centro de distribución.
  • Madre nodriza: un vehículo mayor lleva la carga a puntos de transbordo y los vehículos satélite reparten cada zona desde allí. Ideal para zonas alejadas del depósito.

Las recolecciones se intercalan en la ruta validando que la carga a bordo nunca supere la capacidad del vehículo; si no hay espacio, la recolección se pospone a un punto posterior de la ruta.

POST/optimize
POST /api/v1/optimize
{
  "orderIds": null,             // null = todos los pendientes
  "vehicleIds": ["VEH-1", "VEH-2", "VEH-3"],
  "options": {
    "startTime": "08:30",
    "returnToDepot": true,
    "useNodriza": true
  }
}

→ 201

Prueba de entrega (POD)

Registra la evidencia de entrega o recolección de un pedido. El simulador la genera automáticamente al completar cada parada; también puede registrarse de forma manual.

POST/orders/{id}/pod
POST /api/v1/orders/ORD-1005/pod
{
  "receiver": "María Pérez",
  "method": "firma_digital",    // firma_digital | foto | codigo
  "notes": "Recepción conforme en bodega",
  "failed": false               // true marca el pedido como no_entregado
}
